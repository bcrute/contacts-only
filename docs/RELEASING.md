# Releasing Contacts Only

Status: **released as v1.2.0 on November 5, 2026**, with the new application ID
`com.contactsonly.app`. The release APK is the unsigned build from the 1.2.0
checkpoint in [TESTING.md](TESTING.md), signed with the release key. The 1.1.0
GitHub release (application ID `com.ben.contactsonly`) was published on
November 4, 2026 and withdrawn on November 5 at the owner's request; its tag
remains. Google Play publication is pending.

## Supported Android versions

Android 15 (API 35) and later, while Google still updates them. `minSdk` stays
at 29, so older phones can install the app and it may work there, but they are
not tested and receive no fixes. Release notes must not claim older support.

## Acceptance

Submit `sh ci/validate.sh` with the standalone fleet helper, private fleet
configuration, project `contacts-only`, and Core/Heavy slot controls. On the
current fleet, set `CONTACTS_ONLY_GRADLE_DISTRIBUTION_URL` to the fleet's HTTPS
mirror of `services.gradle.org/distributions/gradle-8.14.3-bin.zip`. Never build
on the development PC or replace a pending check with a local run.

Inspect the accepted job's receipt and download its retained artifacts. A lost
connection after acceptance requires receipt inspection before another submission.
The check must pass build, dependency verification, lint, the API 35/36 regression
tests, the release audit and native Android 16 integration. Native Android 15
integration must pass too, once the fleet has that image; until then its pending
result stays visible in TESTING.md. The release APK is unsigned until the
maintainer signs it; the debug APK generated by a disposable executor is not an
update artifact.

Every passing job also retains the unsigned Google Play app bundle,
`contacts-only/bundle/release/app-release.aab`, listed in its `SHA256SUMS`. The
release audit expands it into the universal APK Play would serve
(`contacts-only/apk_from_bundle/`) and applies the same checks as the release
APK, including an equal version. Upload the bundle from the same accepted job as
the GitHub APK so both stores ship the same source.

## Signing key

GitHub APKs are signed with the dedicated release key:

```text
CN=Android Release, OU=Mobile, O=Deployment (RSA 4096)
SHA-256 3af2d74874186eebc56117df42ddf8d2cb2fc32f042af4b97ebf99cb9db3f9d3
```

The keystore and its password live in a private directory on the maintainer's
PC, outside the repository and fleet snapshots, with an offline backup. That
directory's README holds the exact commands. **Losing the release keystore or
its password means installed copies can never be updated.**

1.0 and 1.1.0 used the old application ID and were signed with the Android
debug key, rotated to the release key for 1.1.0 by an APK Signature Scheme v3
lineage. The new ID is a separate app with no installed copies to carry over,
so 1.2.0 and later need neither the debug key nor the lineage.

To sign a release:

1. Check that the unsigned APK's SHA-256 matches the accepted full fleet job's
   readback manifest and `SHA256SUMS`.
2. Sign with the release key only:

   ```sh
   apksigner sign --ks <release keystore> --ks-key-alias contacts-only-release \
     --out Contacts-Only-<version>.apk app-release-unsigned.apk
   ```
3. Run `apksigner verify --verbose --print-certs`. Expect the release
   certificate above, package `com.contactsonly.app` and the intended
   versionCode and versionName, and record the final SHA-256.

## Google Play

The Play package name is `com.contactsonly.app`, matching the application ID;
neither can change. In Play App Signing, upload the existing release key as the
app signing key rather than letting Google generate one, so Play updates install
over GitHub copies (and the reverse).

Before uploading, check the bundle's SHA-256 against the accepted job's
`SHA256SUMS`, then sign it with the separate upload key using the JDK's `jarsigner`
(apksigner cannot sign bundles), and verify it with `jarsigner -verify`. Raise
`versionCode` for every upload; Play rejects a code it has already seen.

## Phone acceptance

On the Samsung, install the matching signed update over 1.0, then record the
checks in [PHONE-ACCEPTANCE.md](PHONE-ACCEPTANCE.md):

1. Existing call-screening approval and blocking remain on after the upgrade.
2. A saved contact rings; an unsaved caller is rejected and appears in history.
3. Switch off: the same unsaved caller rings. Close/reopen and restart the phone;
   the switch stays off and calls still ring, subject to other phone settings.
4. Switch on: the same caller is rejected again without reinstallation.
5. Revoke the Android call-screening role: the app shows off. Request access and
   cancel: it stays off. Grant it: blocking resumes.
6. Texting, outgoing calls and the existing messaging app continue as before.

## Repository publication

The owner authorized private Gitea source hosting and a public GitHub release.
The destinations are recorded in the maintainer's private handoff; the GitHub
repository is `bcrute/contacts-only`. Inspect for an existing repository before
creating one or changing any remote. Keep Gitea as `origin` and GitHub as
`github`. Do not include the parent's recovery directory or local handoff files
in either repository.

Gitea holds the full development history. Earlier commits name the private
Gitea host, so by owner decision GitHub receives only a snapshot: one commit per
release whose tree equals the released Gitea commit, on top of the previous
snapshot. Commit IDs cited in these documents refer to the Gitea history.
Merge the release branch to `main` explicitly and push `main` and the tag to
Gitea before creating the GitHub snapshot. The software is licensed under MIT
([LICENSE](../LICENSE)).

## GitHub release

After validation, replace `unreleased` in the changelog with the release date,
commit that change, and create an annotated tag such as `v1.2.0` on the accepted source.
Push it to Gitea, and tag the matching GitHub snapshot commit the same way.
Stage the verified, signed artifact as `Contacts-Only-<version>.apk`, with
`SHA256SUMS` computed from that exact APK. Create the GitHub release with
`gh release create <tag> --verify-tag`, attach those two assets, and use that
version's changelog as the release notes. Verify the
published tag's commit and the downloaded APK's checksum. Record the actual
repository/release URLs and CI receipt in the handoff.

Use the version being released in the tag, file and release names. Tag
`v1.1.0` remains on both hosts for the withdrawn release.
